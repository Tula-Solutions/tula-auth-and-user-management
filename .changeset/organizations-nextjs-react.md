The active organization and `has()` in Next.js and React. `@tula-tech/nextjs`: `auth()` returns `orgId`, `orgRole`, `orgPermissions` and `has({ permission } | { role })` (exact match, no wildcard, `false` with no active organization); `tulaMiddleware` takes `access` rules (a route matcher and the permission or role it needs) and `forbiddenUrl`, so a route group can be refused before it renders, with a 403 for an API route; the three organization claims reach `auth()` only as a set that passed the contract's checks, from a verified token, the stateful session's answer and the sealed `x-tula-auth` header alike. A token that carries a maximal role (up to 32 permissions of 100 characters) outgrows one browser cookie (measured: 5.3 kB against a 4,096-byte limit), so the access token is now stored in up to two cookies, `tula_at` and `tula_at_1`, read back in order and verified as one token; a token too large for two is not stored and the session lives on its refresh cookie. `@tula-tech/react`, and `@tula-tech/nextjs` which re-exports them: `useOrganization()` (the active organization, the role and permissions of the session, and `has()`) and `useOrganizationList()` (the user's organizations, `setActive()` and `create()`), keyed to the session so that a result for an earlier session is never shown. `@tula-tech/contract`: `readOrganizationClaims` now checks the organization id, the role key and every permission against the permission grammar, and `hasOrganizationAccess` and the `OrganizationCheck` type are the one `has()` rule every package shares.

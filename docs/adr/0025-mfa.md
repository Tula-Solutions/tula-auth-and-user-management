# ADR 0025 — Two-step verification: TOTP, backup codes, step-up

- Status: accepted
- Date: 2026-10-03
- Builds on [ADR 0004](0004-signing-keys-and-issuer.md) (the secret box and the master key),
  [ADR 0008](0008-sessions.md) (sessions, access-token claims, the denylist),
  [ADR 0011](0011-rate-limits-and-lockout.md) (lockout), [ADR 0012](0012-events-and-audit-log.md)
  (audit), [ADR 0015](0015-password-reset.md) (reset), [ADR 0018](0018-environment-settings.md)
  (settings), [ADR 0019](0019-flow-engine-v2.md) (the hooks this step fills:
  `Factors.requiredFor`, `needs_second_factor`, `Flows.submitSecondFactor`,
  `SECOND_FACTOR_VERIFIERS`), [ADR 0023](0023-security-notices.md) (notices).

## Context

Phase 1 step 1.8 adds the first second factor. It has to exist before OAuth (1.9) and passkeys
(1.10), so that neither can become a way around it. The flow engine was prepared in 1.3: after
every accepted first factor, and after a password reset, it asks which second factors the user
must prove and parks the attempt on `needs_second_factor` with no session and no tokens.

What had to be decided: the factor itself and its parameters; how its secret is stored; what a
used code may still do; what backup codes are; how an app (ours and the developer's) can demand
a *recent* proof for a sensitive action when access tokens are verified offline; what an
environment-wide policy means, especially `off`; and how a user who has lost everything gets
back in.

## Decision

### The factor: TOTP as every authenticator app implements it

- RFC 6238 over HMAC-SHA-1, 6 digits, a 30-second step. These are the only parameters Google
  Authenticator, Authy, 1Password, Microsoft Authenticator and the rest all honour; an app that
  silently ignores `algorithm=SHA256` would show codes that never verify. HMAC-SHA-1 is not
  touched by SHA-1's collision weakness: forging a code still needs the key.
- The implementation is `apps/api/src/lib/totp.ts`: about a hundred lines over `node:crypto`'s
  HMAC, with no dependency, tested against the RFC 4226 and RFC 6238 vectors.
- Secrets are 160 bits from the CSPRNG (the HMAC-SHA-1 key size RFC 4226 recommends), shown as
  Base32 without padding and as
  `otpauth://totp/<issuer>:<account>?secret=…&issuer=…&algorithm=SHA1&digits=6&period=30`. The
  issuer is the environment's `app.name`, the account the user's email, both percent-encoded;
  a colon is dropped from the issuer because the label uses it as the separator.
- **Drift:** a code is right for the current step or one step either side. One step absorbs a
  phone whose clock is slightly off and a code typed as it rolls over; RFC 6238 recommends no
  more. All three candidates are always computed and compared in constant time.
- **Replay:** a factor remembers the last time step it accepted a code for
  (`user_factors.last_used_step`), and a code is accepted only for a **strictly greater** step,
  in one guarded `UPDATE`. So a code works once, a code of an earlier step never works after a
  later one was used, and of two concurrent submissions of the same code exactly one wins. The
  code that confirms an enrolment uses its step up too: it cannot also sign someone in. The
  cost is that two uses of one factor within one step are impossible: a user who signs in and
  is at once asked to step up waits for the next code (at most 30 seconds).

### Storage

- **`user_factors`**, a table of its own rather than a row of `credentials` (which already
  listed a `totp` type). A factor has a lifecycle a password does not: it is *pending* until
  confirmed (`confirmed_at` null, `expires_at` set), it carries the replay counter, and later a
  name. One row per user and type: starting again replaces a pending row, never a confirmed
  one. Starting is **one statement** (`INSERT … ON CONFLICT (user_id, type) DO UPDATE … WHERE
  confirmed_at IS NULL`): two concurrent starts both succeed and leave one pending row, an
  expired pending row is replaced like any other, and only a confirmed factor answers
  `mfa.already_enabled`. A unique violation is never reported as "already enabled". Passkeys
  (1.10) get their own table.
- The secret is sealed with `~/lib/secret-box` (AES-256-GCM under a key derived from
  `TULA_MASTER_KEY` for the purpose `totp-secrets`, apart from the signing keys' key), with the
  environment, the user and the factor's own id as associated data. A ciphertext copied to
  another user's or environment's row does not open; an unopenable secret is treated as a secret
  nobody knows (no code matches) and logged without detail.
- **A pending enrolment counts for nothing.** It is never asked for at sign-in and never
  accepted as a proof. It lapses after ten minutes and the retention job (ADR 0017) deletes it
  an hour after that, per environment, in batches.
- **`backup_codes`**: ten per generation, each ten characters from a 31-character alphabet
  without look-alikes (`0/o`, `1/l/i`), shown as `xxxxx-xxxxx`: about 49.5 bits. Stored **only**
  as `HMAC-SHA256(backup-code key, environment : user : code)` (`~/lib/keyed-hash`, its own
  purpose). The key keeps a database reader from testing guesses offline; binding the hash to
  the user means a copied row matches nothing. Input is normalised (case, spaces, dashes) before
  hashing. A code is spent by one guarded update (`used_at`), so it works exactly once under any
  concurrency. Looking a code up by the equality of its keyed hash is safe without a
  constant-time compare: an attacker cannot compute the hash, so the lookup's timing says
  nothing about the code. All of a user's codes are replaced when regenerated and deleted when
  two-step verification is turned off or reset.
- `sessions` gains `factor_verified_at` and `auth_methods` (below). Migration `0009_mfa`: both
  tables carry tenant columns, the isolation policy with `FORCE ROW LEVEL SECURITY`, and
  `SELECT, INSERT, UPDATE, DELETE` for the runtime role (turning off, resetting, regenerating
  and retention delete on the request path).

### Enrolment (`modules/mfa`, a signed-in user)

| Route | What |
| --- | --- |
| `GET /v1/client/me/factors` | `{ totp: { enabled, confirmedAt }, backupCodes: { remaining } }`. Never a secret. |
| `POST /v1/client/me/factors/totp` | Start: `{ secret, uri }`, **once**. Needs a recent authentication. |
| `POST /v1/client/me/factors/totp/confirm` | `{ code }` → the ten backup codes, **once**. |
| `DELETE /v1/client/me/factors/totp` | Turn off. Needs a recent authentication. |
| `POST /v1/client/me/factors/backup-codes` | Regenerate → ten new codes, **once**. Needs a recent authentication. |
| `DELETE /v1/admin/users/:userId/factors` | Admin reset (secret key). |

Confirming re-checks the policy first (with `mfa.policy: 'off'` an enrolment started before
the switch-off cannot be finished: `mfa.not_available`, before the code is counted). Then, in
one transaction, it marks the factor confirmed, uses the code's step up, replaces the backup
codes and records `user.mfa_enabled`. Every **other** session of the user ends
(they were established without the factor); the session that enrolled is kept and marked as
having proven it. **Order on failure:** the other sessions are ended *before* the factor is
turned on and swept once more after it (as a password reset does). If the first sweep fails
nothing has changed and the same enrolment can be confirmed again; the opposite order could
leave the factor on, a session that never proved it alive, and the backup codes lost with
the failed response. A failure of the second sweep is logged and does not fail the request:
the codes are shown once. The admin reset is ordered the same way for the same reason:
**sessions first, then the factor** (and the sessions once more), so a failure leaves the
factor guarding the account rather than a possibly stolen session outliving it; both steps
are idempotent and the reset is simply repeated. Turning it off oneself ends no sessions, so
it has nothing to order. Every change is audited in the transaction that makes it
(`user.mfa_enabled`, `user.mfa_disabled` with `method: 'self' | 'admin_reset'`,
`user.backup_codes_regenerated`, `user.backup_code_used`) and emailed to the owner best-effort
(`Notices.mfaChanged`, switch `notifications.mfaChanged`, on by default, switching it off is a
weakening). Each kind of change (turned on, turned off, admin reset, new codes, a code used)
has **its own** allowance of three notices an hour: with one shared allowance, enrolling,
using a backup code and making new codes would have silenced "an administrator reset your
two-step verification", which the manual test of this step ran into. No email, audit entry,
log line or error ever contains a secret, a URI or a code.

### Sign-in and password reset

- `Factors.requiredFor` answers `['totp']`, plus `'backup_code'` while an unused code is left,
  for a user with a **confirmed** factor. The verifiers for both are registered in
  `SECOND_FACTOR_VERIFIERS`; the engine did not change shape.
- `POST /v1/client/sign-ins/:attemptId/second-factor` and
  `/password-resets/:attemptId/second-factor`, body `{ method, code }`, authorized by the
  attempt's secret like every flow step. The engine keeps what ADR 0019 promised: per-user
  lockout counted before the proof and cleared on success, the environment's ceiling, the ban
  check, and the compare-and-set that lets one request create the session. No tokens before it.
- A wrong proof is **`mfa.invalid_code`** (422), not `verification.invalid_code`: that code
  tells a client "the emailed code was wrong, offer to resend it", which makes no sense for an
  authenticator.
- **One lockout budget** (`Mfa.secondFactorLockKey`, `CREDENTIAL_LOCKOUT`) for every place a
  TOTP or backup code is checked: the second factor of a sign-in or reset, confirming an
  enrolment, a step-up. Guessing backup codes uses up the guesses at TOTP codes and the reverse.
- A backup code used to sign in is spent, audited, the owner is emailed with the number left,
  and the completed attempt carries `backupCodesRemaining`.
- **A password reset never removes or bypasses the factor.** It stores the new password (the
  inbox was proven) and stops at `needs_second_factor`, as ADR 0019 already had it.

### What a session proved: `auth_time` and `amr`

A session records how it was authenticated, and the access token says so, so that an app's own
backend can demand a recent strong authentication without calling Tula:

- `sessions.factor_verified_at`: when the user last **actively proved a factor** for this
  session. At creation it is the moment the sign-in completed (after its last factor, whichever
  that was); a step-up moves it. Refreshing never does. Rows from before the column read as
  "at creation".
- `sessions.auth_methods`: every method proven for the session so far, added to by step-ups.
- The access token carries them as **`auth_time`** (OpenID Connect's name: epoch seconds, an
  absolute time, because a token is static and an age would be stale the moment it was signed)
  and **`amr`** (RFC 8176): `pwd`, `otp`, `sms` and `mfa` from the RFC, `email` and
  `backup_code` our own. `sms` is a first factor proven with a texted code
  ([ADR 0037](0037-phone-numbers-and-sms.md), added 2026-10-09): a session whose `amr` is
  `sms` alone is never a recent authentication, and `sms` never brings `mfa`. `mfa` is present exactly when a second factor was proven. Examples: `["pwd"]`,
  `["pwd","otp","mfa"]`, `["email"]` (an emailed code or link, a verified sign-up, a reset),
  `["pwd","email"]` (a password sign-in that had to verify the address), `["pwd","backup_code","mfa"]`.
  Both claims are additive and optional in the schema; `v` stays `1`.
- **`amr` is a set.** Its order is not part of the contract: test membership
  (`amr.includes('mfa')`). The server emits one canonical order whatever order things were
  proven in (`pwd`, `email`, `otp`, `backup_code`, `mfa`, then anything else alphabetically;
  `mergeAuthMethods`), only so that tokens and rows are stable. The conformance scenarios
  match it with `{ "$set": [...] }`.

### Step-up

- `POST /v1/client/sessions/step-up` re-proves a factor for the current session, moves
  `factor_verified_at`, and returns a fresh access token (same session, refresh token
  untouched). Audited as `session.stepped_up`.
- **A user with a second factor must step up with it** (`totp` or `backup_code`). Their
  password alone answers `auth.step_up_required`: otherwise a stolen session plus a known
  password would be enough for everything the factor protects. A user without one steps up
  with their password.
- `requireRecentAuth(maxAge = 10 minutes)` reads the **verified access token's claims**:
  `auth_time` within the window, and for a user with a second factor `amr` containing `mfa`.
  The claim is the source of truth because access tokens are verified with no database read and
  live a minute; a step-up hands the client a new one at once. A "revoked step-up" needs no
  handling: revoking is done to sessions, through the denylist, which is checked first.
- The refusal is `auth.step_up_required` (403) with `params.methods`: a comma-separated list of
  what this user can step up with (error params are scalars), so a client can show the right
  prompt. The SDK never prompts by itself.
- Applied to: starting an enrolment, turning two-step verification off, regenerating backup
  codes, and **changing the password of a user who has a second factor** (the current password
  stays required for everyone).
- **Not** applied to "sign out my other devices": it is what a user does when they suspect a
  stolen session, and it grants an attacker nothing. Making it harder helps the wrong side.

### Policy per environment

`mfa.policy: 'off' | 'optional' | 'required'`, default `optional`, exposed by
`/v1/client/config`.

- **`off` hides enrolment; it does not switch existing factors off.** Starting an enrolment
  answers `mfa.not_available`, but a user who already has a factor is still asked for it until
  they or an administrator remove it. Silently dropping a user's second factor because an
  operator changed a setting would be a security regression for that user.
- **`required`:** a user with no factor who passes everything else gets a new step,
  `needs_factor_enrolment { methods: ['totp'] }`, and no tokens. Enrolment then happens inside
  the attempt, authorized by the attempt's secret:
  `…/:attemptId/factor-enrolment/totp` (start) and `…/confirm`, under `sign-ins`, `sign-ups`
  and `password-resets`. Confirming completes the attempt and returns the session and the
  backup codes together, once. A sign-up creates and verifies the account first, then enrols.
  Turning the factor off is refused (`mfa.required_by_policy`).
- **A sign-in that raced an enrolment gets no session without the factor.** An attempt that
  did not prove a second factor re-reads, once its session is created, whether the user has
  one by now (`finish`; not for a sign-up, whose account is created by the same request). If
  a factor was confirmed in between, the confirmation's sweep of "every other session" ran
  before this session existed; so the session is revoked through the session service
  (denylisted), no tokens are returned and the answer is `flow.invalid_step`. The attempt is
  already `complete` and cannot be moved back under the compare-and-set rules: the client
  starts again and is asked for the factor.
- **The factor and the session stand or fall together.** If the attempt cannot complete after
  the factor was confirmed (it expired in that instant, the session could not be created), the
  response that would have carried the backup codes is lost. The enrolment is then undone:
  the factor and its codes are removed (audited as `user.mfa_disabled`, `method:
  'enrolment_incomplete'`, by the system; the delete is guarded by the id of the factor this
  request confirmed, so a factor the user enrolled since is never touched), the error is
  returned, and the user enrols afresh
  at their next sign-in. The owner is told the factor is on only once the attempt has
  completed. If the undo fails as well (both writes failing in a row), the factor stays on
  with codes nobody saw; the user signs in with the authenticator and makes new codes, which
  is tested.
  A hook that refuses the attempt is one more way to get here; that the sessions ended
  first stay ended was looked at again and kept
  ([ADR 0035](0035-hooks.md#what-a-refusal-costs-that-is-easy-to-miss-review-round-1-2026-10-08)).
- Moving towards `off` (`required` → `optional` → `off`) is audited as `weakened`.
- The transition function gained the step, the event `factor_enrolled` and the context field
  `enrolmentRequired`; the exhaustive table classifies every combination.

### Recovery

- A backup code replaces the authenticator once.
- **Lost authenticator and lost backup codes: only an administrator can help**, with
  `DELETE /v1/admin/users/:userId/factors`: the factor and codes are removed, **every** session
  of the user ends, it is audited with the admin as actor and the user is emailed. Under
  `required` the user enrols again at their next sign-in.
- There is deliberately **no emailed bypass**. A reset link that removes the second factor
  turns two factors back into one (the inbox).

## Consequences

- A user without a second factor in an environment with the default policy sees no change in
  behaviour; their tokens gain two claims.
- **After confirming in a profile the access token in hand is stale** (it lacks `mfa`). A
  client refreshes after confirming; `@tula/core` does. Until then a sensitive call asks for a
  step-up, which is safe but annoying.
- An enrolment confirmed inside an attempt that then fails to complete is undone (above). Its
  side effect stays: confirming ended the user's other sessions.
- **The QR code's size.** `@tula/react` draws it 208 px wide where there is room and lets it
  shrink with a narrow card, never below 160 px, with the four-module quiet zone inside the
  drawing so it scales too (a browser test holds this from 1280 px down to a 320 px phone,
  and that the code stays inside its card). It is always dark on white, whatever the theme.
- **A downloaded backup-codes file is given time to be read.** The link is in the document
  when it is clicked and its object URL is revoked a minute later, or when the screen goes,
  not in the same tick: Safari and some Firefox versions read the blob after the click
  returns, and an empty file would be the user's only copy.
- A browser keeps `/v1/client/config` for a minute, so a profile page can offer "Turn off" for
  that long after an operator made the policy `required`; the server refuses it.
- Starting an enrolment is race-safe on Postgres by construction (one upsert); the suite
  proves it on the memory adapter and on PGlite, which run one connection. It has not been
  exercised with two real connections.
- **A user with neither a password nor a second factor had no step-up method**
  (`params.methods` was empty), so someone who signed up through a provider or by email could
  not enrol a second factor or change a connected account once their sign-in was ten minutes
  old. *Closed by the addendum below ("Step-up by emailed code").* What remains: a user with no
  password, no second factor **and no verified address** still has none, and signs in again.
- Rotating `TULA_MASTER_KEY` makes sealed secrets unopenable and backup-code hashes unmatchable:
  every user's second factor stops verifying and needs an admin reset. Key rotation with
  re-sealing is out of scope here, as it is for signing keys.
- `off` leaves already-enrolled users enrolled, so an operator who wants MFA gone has to reset
  those users.
- Step-up age is one constant (`STEP_UP_MAX_AGE_SECONDS`, 600). Session profiles (1.11) make
  it a per-profile rule.

### What is not here

- **SMS.** SIM swapping and delivery cost; `sms_code` stays an unprovable method.
- **Email as a second factor.** For most users the inbox is already the recovery channel and
  often the first factor.
- **WebAuthn as a second factor.** It comes with passkeys in 1.10 (the `passkey` method has no
  verifier yet).
- **Remembered devices** ("don't ask again on this browser for 30 days"). It needs device
  binding, which sessions do not have yet.
- **More than one authenticator per user**, and renaming one: the table allows a name; nothing
  sets it.

## Addendum (step 1.9): step-up by emailed code

**Decision.** A user with a verified email address and **no confirmed second factor** may step
up with a 6-digit code emailed on request. `Mfa.stepUpMethods` is the one place that decides
it: a second factor when there is one (and then nothing else), otherwise `password` when the
user has one and `email_code` when their address is verified. `params.methods` of
`auth.step_up_required` lists exactly that.

- `POST /v1/client/sessions/step-up/email-code` (session-authenticated) sends the code and
  answers with a receipt (masked destination, expiry), never the code. Anyone who may not use
  it gets `auth.step_up_required` with what they can use, and no email.
- `POST /v1/client/sessions/step-up` accepts `{ "method": "email_code", "code": "…" }`. Success
  records `email` in the session's `amr` (the same value the emailed first factor records) and
  moves `auth_time`; it never adds `mfa`.
- The code is a verification token (ADR 0007) of its own purpose, `step_up`: ten minutes, five
  guesses, single use, replaced by a newer one, stored as `HMAC(key, "<token id>:<session
  id>:<code>")`. The session id in the hash is what binds it: a code asked for by one session
  checks out for no other, with no new column. The purpose is what keeps it apart: a `step_up`
  code is honoured by no flow, and no flow's code steps up. It carries no link.
- **Limits.** Sending: the route's per-IP limit, and one a minute and five an hour **per
  user**, under limiter keys of their own (`step_up_email_cooldown:<environment>:<user>`,
  `step_up_email:<environment>:<user>`). They are deliberately not the per-address cooldown and
  hourly limit of the sign-in, reset and verification codes (ADR 0007): those codes can be
  asked for without signing in, so a shared budget would let anyone who knows a user's address
  keep that user's step-up emails refused, which for a passwordless user is every protected
  action. The reverse holds too: step-up sends use up nothing of the address's budget. A
  limiter that cannot answer sends nothing (`service.unavailable`). Guessing: the token's own five
  guesses, and before the check a count against the per-user lockout key the password step-up
  uses (`step_up:<environment>:<user>`, `CREDENTIAL_LOCKOUT`), cleared on success. One key for
  both, so the two cannot be guessed in turn; **not** `secondFactorLockKey`, whose budget
  belongs to users who have a second factor.
- The session is checked to be live before the token is touched, so a revoked session spends
  no code. The token's destination must still be the account's verified address.
- Audit: the existing `session.stepped_up` entry (`methods: ["email"]`). No code, no address.

**Threat model.** What the step-up protects for these users is: enrolling a second factor, and
connecting or disconnecting a provider account.

- *A stolen session (token theft, an unlocked laptop), no mailbox access.* Before: blocked
  after ten minutes for a passwordless user (no method at all) and for a password user who
  kept the password secret. After: the same. The attacker cannot read the code.
- *A stolen session and the mailbox.* The attacker can step up. They could already take the
  account over without the session: a password reset and an emailed sign-in are both proven by
  that mailbox alone. For a user without a second factor the mailbox **is** the account's
  root of trust; the emailed step-up is exactly as strong as that weakest first factor, and
  not weaker.
- *A password user: does the emailed code weaken "session plus password"?* It changes the bar
  from "knows the password" to "knows the password or reads the mailbox". Reading the mailbox
  already resets the password, so the set of attackers who can act does not grow. It is offered
  to them (as the other way, sent only on request) so that a forgotten password does not lock
  a signed-in user out of adding a second factor. **The trade-off, stated plainly:** it is
  equivalent to what the mailbox already allows through a reset, but not identical. A reset
  changes the password, ends the other sessions and is announced to the owner; the emailed
  step-up does none of that. The residual is an attacker with a stolen live session **and**
  the mailbox open, who no longer needs the password (or a noisy reset) to connect a provider
  account or enrol a second factor. Both of those are themselves announced to the
  owner, and it is never available to a user who has a second factor.
- *A user with a second factor.* Never offered, never accepted, including a code emailed before
  the factor was confirmed: `stepUpMethods` is asked again at the proof. Otherwise the mailbox
  would bypass the factor, which a password reset is also not allowed to do.
- *Cross-session and cross-purpose replay.* The session binding and the purpose (above).
- *Guessing.* 10^6 codes, five guesses a token, five tokens an hour, and the per-user lockout
  across both non-MFA methods.
- *Mail flooding.* One a minute and five an hour per user, on top of (not inside) what the
  address may be sent by the unauthenticated flows; only the signed-in owner's own address can
  be sent to.
- *Keeping a user from stepping up.* Not possible from outside the account: the send limits
  are per user and only that user's sessions count against them (above). What remains is
  between the user's **own sessions**. The token is found per user and purpose, so a second
  session of the same user that asks for a code replaces the first session's, and its wrong
  guesses use up the guesses of a code it cannot itself pass (the hash is bound to the asking
  session). An attacker holding one of the user's sessions can therefore delay a step-up in
  another, never perform one. This is accepted as an availability-only residual, bounded by the
  per-user lockout and the send cooldown; scoping the token to the session would need a new
  subject column on `verification_tokens`.
- *Enumeration.* None: the caller is signed in and learns only about themselves.

**Clients.** `@tula/core`: `session.prepareStepUp({ method: 'email_code' })` and
`session.stepUp({ method: 'email_code', code })`; the SDK never sends the email by itself.
`@tula/react`: the provider's step-up dialog sends the code when the user chooses it next to a
password, and at once (once, also under StrictMode) when it is the only method. The code field
is drawn only after a send of that dialog succeeded: a refused send (the cooldown included)
shows the error with the server's wait counted down and a "Send code" button, never "we sent
you a code".

**Also here.** `GET /v1/client/me` answers a `CurrentUser`: the user plus `hasPassword`, so a
profile can tell a passwordless user how to add a password (a password reset creates the first
one, ADR 0019) instead of asking for a current one. No new route was added for that.
